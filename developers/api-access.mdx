title: "Scoped API access with an API signer"
description: "Generate a scoped API signer on the Developers page, sign requests with EIP-191, and call the People API to sync recipients programmatically."
---

Archer exposes a small programmatic API for managing people (the recipients of rewards and payouts) in your workspace. Access is authenticated with an **API signer** — a dedicated EVM key pair that you generate on the Developers page and use to sign every request. Archer stores only the signer address and its scopes; the private key never leaves your machine.

Use this when you need to sync people from your own systems into Archer without having a human sign in to the dashboard.

## Prerequisites

- An Archer workspace with **Admin** access. Recipient-only accounts can't create signers.
- A completed onboarding — the API rejects signer requests until your workspace is active.
- A secret manager (or equivalent) to store the signer's private key.

## 1. Generate an API signer

Open the **Developers** page in the dashboard and find the **API signer** card.

1. Enter a **name** for the signer — pick something that identifies where you'll use it (for example, `production-sync` or `staging-worker`). Names help you tell signers apart if you rotate them.
2. Select **Generate API signer**. Your browser generates a new EVM key pair locally, signs a short-lived registration challenge with the private key to prove ownership, and sends only the public address and signature to Archer. The private key never leaves the page.
3. Copy the private key into your secret manager immediately — it's displayed **once**. If you lose it, generate a new signer.
4. Under **API scopes**, check the scopes this signer should be allowed to use, then select **Save API scopes**. New signers have no permissions until you assign at least one scope.

Each workspace can have one active signer at a time. Rotating the key and revoking access are on the roadmap.

### Available scopes

| Scope | Grants |
|---|---|
| `person:read` | `GET /person` — list people, or fetch a single person with `?person_id=…`. |
| `person:write` | `POST /person` — create a person and provision their wallet. |

Requests without a scope the endpoint requires return `403 Forbidden` with code `insufficient_scope`.

## 2. Sign a request

Every call to a scoped endpoint must include four headers:

| Header | Value |
|---|---|
| `x-archer-signer-address` | The signer's EVM address, exactly as shown on the Developers page. |
| `x-archer-timestamp` | Current Unix time in seconds. Requests more than five minutes off from Archer's clock are rejected. |
| `x-archer-nonce` | A unique 16–128 character value (letters, digits, `._~-`). Reused nonces are rejected for 10 minutes. |
| `x-archer-signature` | An EIP-191 (`personal_sign`) signature over the canonical message below, produced by the signer's private key. |

Build the canonical message by joining these lines with `\n`:

```
archer-api-v1
<host — for example api.archermoney.com, lowercased>
<HTTP method, uppercased — for example GET or POST>
<request path — for example /person>
<canonical query string — sorted key=value pairs joined with &, empty for no params>
<sha256 hex digest of the request body — empty string when there is no body>
<x-archer-timestamp value>
<x-archer-nonce value>
```

Then sign that string with EIP-191 and pass the resulting `0x…` signature in `x-archer-signature`.

### Node.js example

```js
import { createHash, randomBytes } from "node:crypto";
import { Wallet } from "ethers";

const wallet = new Wallet(process.env.ARCHER_API_SIGNER_KEY);
const host = "api.archermoney.com";
const method = "GET";
const path = "/person";
const query = ""; // e.g. "include_archived=true"
const body = ""; // stringified JSON for POST/PUT

const timestamp = Math.floor(Date.now() / 1000).toString();
const nonce = randomBytes(16).toString("hex");
const bodyHash = createHash("sha256").update(body).digest("hex");

const message = [
  "archer-api-v1",
  host,
  method,
  path,
  query,
  bodyHash,
  timestamp,
  nonce,
].join("\n");

const signature = await wallet.signMessage(message);

const response = await fetch(`https://${host}${path}`, {
  method,
  headers: {
    "x-archer-signer-address": wallet.address,
    "x-archer-timestamp": timestamp,
    "x-archer-nonce": nonce,
    "x-archer-signature": signature,
  },
});
```

For requests with a body, JSON-serialize it once, use that exact string as the body Archer receives **and** for the sha256 in the signed message.

## 3. Call the API

### List people

```bash
curl "https://api.archermoney.com/person" \
  -H "x-archer-signer-address: 0x…" \
  -H "x-archer-timestamp: 1721775600" \
  -H "x-archer-nonce: 9f8e7d6c5b4a3210" \
  -H "x-archer-signature: 0x…"
```

Optional query parameters:

- `person_id` — fetch a single person by ID.
- `include_archived=true` — include archived people in the list.
- `include_all_states=true` — include people in non-active states.

### Create a person

```bash
curl -X POST "https://api.archermoney.com/person" \
  -H "Content-Type: application/json" \
  -H "x-archer-signer-address: 0x…" \
  -H "x-archer-timestamp: 1721775600" \
  -H "x-archer-nonce: 9f8e7d6c5b4a3210" \
  -H "x-archer-signature: 0x…" \
  -d '{"email":"alice@example.com","name":"Alice Example"}'
```

`email` is required and must be unique within your workspace. Archer pregenerates a wallet for the person on creation and returns their `id`, `wallet_address`, and status.

## Common rejection reasons

Archer returns `401 Unauthorized` or `403 Forbidden` with a `code` field when a signed request can't be verified:

| Code | Meaning |
|---|---|
| `missing_api_signer_headers` | One of the four `x-archer-*` headers isn't set. |
| `invalid_api_signer_address` | The address isn't a valid checksummed EVM address. |
| `invalid_api_signer_timestamp` | Timestamp isn't a Unix integer, or it's off by more than five minutes. |
| `expired_api_signer_request` | Same as above — clock skew is out of the ±5 minute window. |
| `invalid_api_signer_nonce` | Nonce is the wrong length or contains disallowed characters. |
| `invalid_api_signer_signature` | The recovered signer address doesn't match `x-archer-signer-address`, or the signed message doesn't match the request. |
| `unknown_api_signer` | The signer address isn't registered on any workspace, or has been revoked. |
| `recipient_not_allowed` | Recipient accounts can't use the API. |
| `not_onboarded` | Your workspace hasn't finished onboarding. |
| `insufficient_scope` | The signer isn't assigned the scope the endpoint requires. |

Match the message you sign to the exact request you send — the wrong host, path, query ordering, or body serialization will fail verification.

title: "Send events"
description: "Best practices for sending events to Archer reward webhooks: payload conventions, idempotency keys, exponential backoff retries, and debugging tips."
---

This guide covers the producer side of an Archer integration: how to send events reliably so your rewards fire exactly once per real-world signal.

## Endpoint

Every reward has its own URL:

```
POST https://api.archermoney.com/events/{webhook_token}
Content-Type: application/json
```

No `Authorization` header — the URL itself is the secret. Treat it like an API key:

- Store it in environment variables, not in source.
- Rotate it (by recreating the reward) if you suspect a leak.
- Don't include it in client-side bundles or logs.

## Payload conventions

Archer accepts any JSON object up to 100 KB. Two fields are reserved by convention:

```json
{
  "event_id": "evt_2026_05_20_abc",
  "type": "referral.converted",
  "referrer_email": "alice@example.com",
  "amount_usd": 25
}
```

- **`event_id`** — your idempotency key. Required for safe retries.
- **`type`** — short, dotted string for observability. Logged at ingress.

Everything else is application-specific. Put whatever the reward needs to act — emails, identifiers, amounts, metadata.

## Idempotency

Archer dedupes on `(event_id, agent_id)`. If your producer retries the same `event_id`, the second call is a no-op.

```text
First  POST → 202 Accepted, reward runs
Second POST → 202 Accepted, EventRun already exists, no side effects
```

If you omit `event_id`, every retry creates a new `EventRun`. **Always set it** when your transport can retry — HTTP timeouts, queue redelivery, cron job retries.

A good `event_id` is:

- Stable for a single real-world event
- Unique across your producers (use a prefix like `crm-`, `ci-`, `app-`)
- ≤ 128 characters

## Retries

The endpoint returns `202 Accepted` once the event is enqueued. Treat any other status as retryable:

| Status | Meaning | Retry? |
|---|---|---|
| `202` | Accepted | No |
| `400` | Invalid JSON or bad request | No — fix the payload |
| `404` | Discriminant not recognized | No — check the URL |
| `405` | Wrong HTTP method | No |
| `413` | Payload over 100 KB | No — shrink the payload |
| `5xx` | Server error | Yes, with exponential backoff |

Aim for exponential backoff with jitter and a cap on retries (5–10 attempts over a few minutes is usually enough).

## Verifying delivery

After a `202`, check the [Activity](/concepts/activity) page or `GET /activity` for the resulting reward. Webhook events from a paused reward are acknowledged and dropped silently — they will not appear in Activity.

If a reward is not firing, work backwards:

1. Confirm the reward is `active` (`GET /agent?agent_id=...`).
2. Confirm your `webhook_url` matches the reward's `webhook_url`.
3. Send a test event with a unique `event_id` and check the response.
4. Check your producer's logs for the response body — Archer returns the discriminant it parsed.

## Local testing

Use `curl` or [HTTPie](https://httpie.io/) to simulate events from a developer machine:

```bash
curl -X POST "$WEBHOOK_URL" \
  -H "Content-Type: application/json" \
  -d "{\"event_id\":\"test_$(uuidgen)\",\"type\":\"test\"}"
```

You can post the same `event_id` twice to verify idempotency, or change it to force a fresh run.
